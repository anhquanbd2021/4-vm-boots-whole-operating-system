Concept guide

Two switches, one kernel.

A container isn't a small VM. It's an ordinary Linux process running under two kernel controls: namespaces decide what it can see, cgroups decide what it can use.

Try: in Lab 1, switch user off — the panel warns that root inside is root on the host. That's the default without a user namespace.

The cgroup leash

Namespaces hide; cgroups enforce. A budget of memory and CPU per tick is applied by the kernel itself — the process is never consulted. Exceed memory and the OOM killer ends the process at that tick; ask for more CPU than the quota and the kernel grants the quota, so the same work takes more ticks.

Try: run leaky-app (OOM at the tick where cumulative memory crosses 256 MB), then cpu-hog (completes, but slower than its ideal). Check "no limits" and the leak runs free — that's a real host's default.

Why ~50 ms

A VM pays for firmware, a bootloader, a kernel decompress, an init system, and userspace before the app starts — seconds of work per instance, plus a guest OS in memory forever. A container pays for clone() (namespaces + cgroups flipped in one call) and execve(). Nothing boots because the kernel is already running. That's the speed — and the honest trade: everyone shares that kernel, so a kernel exploit escapes to the host. A container is isolation, not a security boundary.
